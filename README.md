# PatternShield (CyberSentinel)

A simplified Web Application Firewall (WAF) built with Flask that inspects
incoming HTTP requests for SQL Injection, XSS, and Path Traversal patterns
and blocks them before they reach the application — with an admin
dashboard, a real SQLite-backed login to demonstrate why parameterized
queries matter, and a labeled-dataset benchmark for measuring detection
accuracy. Built as a college mini-project: simple, readable, and fully
explainable.

## How it works

1. `app.py` runs a small "vulnerable" demo app: a login form (backed by a
   real SQLite table), a search box, and a file-fetch endpoint.
2. `waf.py` registers a Flask `before_request` hook — middleware that runs
   **before every single route handler**, for every request.
3. On each request, the WAF checks the URL path, every query-string
   parameter, and every submitted form field against regex rules for SQL
   Injection, XSS, and Path Traversal.
4. If anything matches, the WAF logs the attempt to `logs/waf_log.json`
   (timestamp, attack type, matched pattern, payload, source IP, blocked
   URL) and returns an HTTP 403 "Blocked by WAF" page — the route's own
   code never runs.
5. If the request is clean, the WAF does nothing and Flask continues to
   the normal route handler.
6. `/dashboard` (admin-only) reads `logs/waf_log.json` and shows a table
   of every blocked attempt (most recent first), per-attack-type counts,
   an attacks-per-day chart, a top-source-IP chart, and the latest
   detection-accuracy benchmark.

## Setup

```bash
python -m venv venv
source venv/bin/activate        # on Windows: venv\Scripts\activate
pip install -r requirements.txt
python app.py
```

The app runs at http://localhost:5000

## Trying it out

- Visit http://localhost:5000 and try the login form, search box, and
  fetch-file endpoint with normal input — everything should work fine.
- Then try the same pages with malicious input, e.g.:
  - Login username: `' OR '1'='1' --`
  - Search: `<script>alert(1)</script>`
  - Fetch file: `../../../../etc/passwd`
- Each of these should be rejected with a "Blocked by WAF" 403 page.
- Visit http://localhost:5000/admin/login (demo credentials:
  `admin` / `waf-admin123`) to reach the dashboard.

## Automated test script

With the server running, in another terminal:

```bash
./test_attacks.sh
```

This fires one clean baseline request plus two sample payloads for each
of the three attack types and prints the HTTP status code returned for
each. The malicious ones should all come back `403`; the clean one
should come back `200`. Afterwards, check `/dashboard` to see them all
logged.

## Demo: why a WAF *and* safe queries both matter

Log in as admin, go to **Admin → Settings**, and you'll find two
independent toggles:

| WAF | Query mode | Result of `' OR '1'='1' --` on /login |
|-----|------------|----------------------------------------|
| Enabled | Either | Blocked with 403 before `/login` ever runs |
| Disabled | Safe (parameterized) | Reaches `/login`, but the query treats the payload as plain text — login fails |
| Disabled | Vulnerable (raw SQL) | Reaches `/login`, the payload rewrites the query — login **succeeds** (bypass!) |

This is backed by a real SQLite `users` table (`database.py`), not a
simulation — `check_login_vulnerable()` builds SQL with an f-string (the
textbook bug), `check_login_safe()` uses `?` placeholders (the fix).
Demo accounts: `admin / admin123`, `alice / wonderland`.

## Measuring detection accuracy

```bash
python evaluate_waf.py
```

Runs every payload in `dataset/test_payloads.json` (18 SQLi, 18 XSS, 14
Path Traversal, 30 clean/benign strings — some of the "clean" ones are
deliberately tricky, e.g. containing `;` or `--`, to surface false
positives honestly) through the WAF's `scan_value()` and reports
accuracy plus per-class precision/recall/F1. Results are written to
`dataset/results.json` and shown on `/dashboard`. Current run: **~89%
overall accuracy** — see the printed mismatch list for exactly which
payloads the regex rules miss or over-flag, which is good material for
explaining the detection trade-offs in your report.

## Detection rules (waf.py)

| Attack Type      | Example patterns checked                                   |
|-------------------|--------------------------------------------------------------|
| SQL Injection      | `' OR 1=1`, `UNION SELECT`, `DROP TABLE`, `--`, `;`         |
| XSS                | `<script>`, `onerror=`, `onload=`, `javascript:`, `<img src=x onerror=...>` |
| Path Traversal     | `../`, `..\`, `%2e%2e%2f`, `/etc/passwd`                    |

These are plain regular expressions, intentionally simple so they're
easy to read and explain. A production-grade WAF (e.g. OWASP
ModSecurity Core Rule Set) uses far more sophisticated detection — this
project demonstrates the *concept* of request interception,
pattern-based detection, logging, and the limits of signature-based
defenses (see the benchmark above).

## Notes / limitations (good to mention when presenting)

- Regex-based detection has real false positives and false negatives —
  `evaluate_waf.py` quantifies both instead of hand-waving about them.
  For example the `--` and `;` rules over-trigger on ordinary text
  ("version 1.0 -- stable release"), while payloads using letters
  instead of digits (`' OR 'a'='a'`) or mixed encodings slip through.
- The admin toggles in `/admin/settings` (disabling the WAF, switching
  to a vulnerable query) exist purely to demonstrate the vulnerability
  live. They, and the hardcoded admin password, must never exist in a
  real deployment.
- The JSON log file and in-memory settings aren't safe for concurrent
  writes at scale — used here instead of a real database/config store
  to keep the project dependency-free and easy to inspect/explain.
